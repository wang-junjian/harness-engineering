核心原理

Harness Engineering 是设计使 AI 智能体可靠工作的系统——不仅仅是控制，更是赋能。

马具隐喻

"Harness"一词源于马具——缰绳、鞍具、嚼子——这套完整装备用于驾驭强大但不可预测的动物。

马

AI 模型

强大、快速，但不知道方向

具

基础设施

约束、护栏、反馈循环

人

人类工程师

提供方向，而非奔跑

形式化定义

Harness Engineering 是设计和实现以下系统的学科：

1 约束 (Constrain) — 限制 AI 能做什么
2 告知 (Inform) — 提供上下文和目标
3 验证 (Verify) — 检查是否正确完成
4 纠正 (Correct) — 错误时的反馈循环

核心洞察：模型是商品，Harness 是护城河

AI 行业的核心事实是：底层模型的重要性低于围绕它的系统。LangChain 仅通过改变 Harness，将 Terminal Bench 2.0 得分从 52.8% 提升到 66.5%（Top 30 → Top 5），模型本身完全未变。

技术架构

Harness Engineering 的三大支柱：上下文工程、架构约束与熵管理。

1

上下文工程

确保智能体在正确的时间获得正确的信息

  • 静态上下文：文档、AGENTS.md
  • 动态上下文：可观测数据、目录结构
  • CI/CD 状态和测试结果
2

架构约束

机械性地强制执行"好代码"的标准

  • 依赖分层规则
  • 确定性 Linter
  • 结构化测试
3

熵管理

对抗代码库的"熵增"——腐化与漂移

  • 文档一致性代理
  • 约束违规扫描
  • 模式强制执行

实践指南

从个人开发者到工程组织，渐进式构建你的 Harness。

L1

基础 Harness（个人开发者）

1-2 小时

使用 Claude Code、Cursor 或 Codex 进行个人项目开发

必须设置

  • • CLAUDE.md 或 .cursorrules 项目规范
  • • Pre-commit hooks（lint/format）
  • • 智能体可运行的测试套件
  • • 清晰的目录结构与命名规范

效果

  • • 防止最常见的智能体错误
  • • 提升代码风格一致性
  • • 快速验证代码正确性
L2

团队 Harness（小团队 3-10 人）

1-2 天

团队共享代码库，智能体行为需要跨成员一致

在 L1 基础上添加

  • • AGENTS.md 团队级规范
  • • CI 强制架构约束
  • • 共享 prompt 模板
  • • 文档即代码（linter 验证）
  • • 智能体 PR 审查清单

效果

  • • 跨团队智能体行为一致
  • • 架构漂移被自动阻止
  • • 文档始终保持最新
L3

生产 Harness（工程组织）

1-2 周

数十个并发智能体运行，需要完整的监控与治理

在 L2 基础上添加

  • • 自定义中间件层（循环检测等）
  • • 可观测性集成（日志/指标/追踪）
  • • 熵管理代理（定时运行）
  • • Harness 版本控制与 A/B 测试
  • • 智能体性能监控面板
  • • 升级策略（智能体卡住时）

效果

  • • 智能体作为自主贡献者
  • • 实时洞察智能体行为
  • • 代码库长期健康可维护

常见错误

❌

过度工程化控制流

"如果过度工程化控制流，下次模型更新会破坏系统。"模型进步很快，2024 年需要复杂管道的功能现在可能只需一个提示就搞定。

❌

将 Harness 视为静态

Harness 需要随模型演进。每次重大模型更新时审查和更新 Harness 组件。

❌

忽视文档层

最有效的 Harness 改进往往最简单：更好的文档。如果 AGENTS.md 模糊，智能体输出就会模糊。

❌

没有反馈循环

没有反馈的 Harness 是笼子，不是指南。构建自验证步骤、测试执行、成功率指标。

相关概念对比

概念 范围 焦点
提示工程 单次交互 制作有效提示
上下文工程 模型上下文窗口 模型能看到什么信息
Harness 工程 整个智能体系统 环境、约束、反馈、生命周期
智能体工程 智能体架构 内部设计与路由
平台工程 基础设施 部署、扩展、运维

Harness 工程包含上下文工程，借鉴提示工程，但处于更高层级——它是关于使智能体可靠工作的完整系统，而不仅仅是单次交互的输入。
