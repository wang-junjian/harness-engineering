核心概念

什么是 Harness Engineering？

Harness Engineering 是设计和实现系统的学科，这些系统能够：

  • 约束：定义 AI 智能体可以做什么（架构边界、依赖规则）
  • 告知：告诉智能体应该做什么（上下文工程、文档体系）
  • 验证：检查智能体是否正确完成任务（测试、linting、CI 验证）
  • 修正：当智能体出错时引导其自我修复（反馈循环、自我修正机制）

核心原理

前馈与反馈双循环

graph TD A[前馈控制
事前引导] --> B[智能体执行任务] B --> C[反馈控制
事后验证] C --> D[修正与优化] D --> B style A fill:#eff6ff,stroke:#3b82f6 style C fill:#fef2f2,stroke:#ef4444

Harness Engineering 的核心是通过前馈控制和反馈控制的组合来规范智能体行为。 只有前馈没有反馈，智能体会重复同样的错误；只有反馈没有前馈，智能体编码规则但永远不知道是否有效。

计算型与推理型控制

特点 确定性、速度快 语义分析、非确定性
执行方 CPU GPU/NPU
适用场景 需要快速、确定检查 需要主观判断、语义理解
例子 测试、linters、类型检查 AI 代码评审、需求理解

可维护性 Harness

监管内部代码质量和可维护性，计算型传感器可靠地捕获结构性问题， LLM 可以部分解决需要语义判断的问题。

架构适配性 Harness

定义和检查应用的架构特性，包括性能要求的技能和性能测试， 可观测性编码约定和调试指令。

行为 Harness

引导和感知应用功能行为是否符合预期，是目前最大的挑战， 需要找到更好的方法来构建功能行为的 Harness，减少监督和手动测试。

上下文工程

确保智能体在正确的时间获得正确的信息，包括静态上下文和动态上下文。

关键规则：从智能体的角度来看，任何它在上下文中无法访问的内容都不存在。 仓库必须是唯一的真实来源。

架构约束

机械地强制执行好代码的样子，而不是仅仅告诉智能体"写好代码"。

Types → Config → Repo → Service → Runtime → UI

每层只能从其左侧的层导入，由结构测试和 CI 验证强制执行。

熵管理（垃圾回收）

定期清理 AI 生成的代码库中积累的熵：文档与现实脱节、命名约定不一致、死代码堆积。

定期运行后台智能体任务，扫描偏差、更新质量等级、发起有针对性的重构 PR， 每天发现并解决不良模式。

规划器 (Planner)

将简单的 1-4 句提示扩展为完整的产品规范，专注于产品上下文和高层技术设计， 而不是详细的技术实现。

生成器 (Generator)

一次实现一个特性，每个 sprint 结束时自我评估工作，然后交给 QA。 与评估器协商 sprint 合同，就"完成"定义达成一致。

评估器 (Evaluator)

使用 Playwright MCP 像用户一样点击运行中的应用，测试 UI 功能、API 端点和数据库状态， 根据发现的 bug 和一组标准对每个 sprint 进行评分。

Stripe 的内部编码智能体"Minions"现在每周产生超过 1,000 个合并的 PR。 从任务发布到 PR 合并之间不需要开发者交互，Harness 处理所有事情 —— 测试执行、CI 验证、风格合规性和文档更新。

LangChain：中间件优先架构

Agent Request
  → LocalContextMiddleware (映射代码库)
  → LoopDetectionMiddleware (防止重复)
  → ReasoningSandwichMiddleware (优化计算)
  → PreCompletionChecklistMiddleware (强制执行验证)
  → Agent Response

LangChain 将他们的 Harness 构建为可组合的中间件层，每个中间件层添加特定功能， 而不修改核心智能体逻辑。这种模块化方法使 Harness 可测试和可演进。

最佳实践指南

文档体系最佳实践

  • AGENTS.md 作为地图，而不是百科全书

    保持 AGENTS.md 简短（约 100 行），作为内容目录，详细知识放在结构化的 docs/ 目录中。

  • 文档验证与自动维护

    使用 linter 和 CI 作业验证知识库的更新状态、交叉链接和结构正确性。 定期运行"文档园艺"智能体，扫描过时或废弃的文档。

  • 仓库必须是唯一真实来源

    所有架构决策、命名约定、部署流程都必须在仓库中，任何智能体需要的信息都不能存储在 Slack 或 Google Docs 中。

约束设计最佳实践

  • 分层架构强制执行

    每个业务领域划分为固定层：Types → Config → Repo → Service → Runtime → UI， 依赖方向经过严格验证，通过自定义 linter 和结构测试机械地执行。

  • 明确限制与自由的边界

    中央层面强制执行边界、正确性和可重复性，在边界内允许智能体在解决方案表达上有很大自由。 只要输出正确、可维护且对未来智能体运行清晰可读，就符合标准。

反馈循环最佳实践

graph TD A[规划与发现] --> B[构建] B --> C[验证] C --> D{通过?} D -->|是| E[完成] D -->|否| F[修复] F --> B style A fill:#eff6ff,stroke:#3b82f6 style C fill:#f0fdf4,stroke:#10b981 style F fill:#fef2f2,stroke:#ef4444
  • 强制构建-验证循环

    强制智能体遵循"规划与发现 → 构建 → 验证 → 修复"的工作流， 使用 PreCompletionChecklistMiddleware 在智能体退出前拦截，提醒其进行验证。

  • 上下文主动注入

    代理启动时自动映射当前工作目录和父/子目录，自动发现可用工具， 注入时间预算警告，促使智能体完成工作并转向验证。

熵管理最佳实践

  • 定期垃圾回收

    定期运行后台智能体任务，扫描偏差、更新质量等级、发起有针对性的重构 PR。 将"黄金原则"直接编码到代码库中，建立循环清理流程。

  • 人类品味持续反馈

    审查评论、重构 PR 和面向用户的 Bug 被记录为文档更新，或直接编码到工具中。 当文档不够完善时，将规则转化为代码。

实施路线图

1

基础 Harness（个人开发者）

1-2 小时

如果你在个人项目中使用 Claude Code、Cursor 或 Codex：

  • CLAUDE.md 或 .cursorrules 文件，包含项目约定
  • 用于 linting 和格式化的 pre-commit 钩子
  • 智能体可以运行以进行自我验证的测试套件
  • 清晰的目录结构和一致的命名
影响：防止最常见的智能体错误
2

团队 Harness（小团队）

1-2 天

对于共享代码库的 3-10 人开发团队，在层级 1 基础上添加：

  • 包含团队范围约定的 AGENTS.md
  • 由 CI 强制执行的架构约束
  • 常见任务的共享提示模板
  • 由 linters 验证的文档即代码
  • 专门针对智能体生成 PR 的代码审查清单
影响：整个团队的智能体行为一致
3

生产 Harness（工程组织）

1-2 周

对于运行数十个并发智能体的组织，在层级 2 基础上添加：

  • 自定义中间件层（循环检测、推理优化）
  • 可观测性集成（智能体读取日志和指标）
  • 按计划运行的熵管理智能体
  • Harness 版本控制和 A/B 测试
  • 智能体性能监控仪表盘
  • 智能体陷入困境时的升级策略
影响：智能体作为自主贡献者运行

这并不意味着工程师的技术性降低。相反，Harness 工程需要更深的架构思维 —— 你设计的系统必须在没有你持续干预的情况下工作。

关键技能需求

  • 系统思维

    理解约束、反馈循环和文档如何相互作用

  • 架构设计

    定义可执行且富有成效的边界

  • 规范编写

    足够精确地表达意图，以便智能体执行

  • 可观测性

    构建揭示智能体行为模式的监控

  • 迭代速度

    快速测试和完善 Harness 配置

常见陷阱与避免方法

  • 过度工程控制流

    模型发展迅速，构建可"剥离"的 Harness，当模型变得足够智能时，能够移除"智能"逻辑。

  • 将 Harness 视为静态

    Harness 需要与模型一起进化，每次主要模型更新时，审查和更新 Harness 组件。

  • 忽视文档层

    最有影响力的 Harness 改进通常是最简单的：更好的文档。如果你的 AGENTS.md 含糊不清，智能体输出也会含糊不清。

  • 没有反馈循环

    没有反馈的 Harness 是笼子，不是指南。智能体需要知道何时成功，何时失败。

  • 仅面向人类的文档

    如果你的架构决策存在于人们的头脑中或智能体无法访问的 Confluence 页面中，Harness 就有缺口。

总结

Harness Engineering 是 AI 时代软件工程的新范式。随着 AI 模型变得越来越强大，如何设计系统来引导、约束和利用这些模型的能力， 将成为决定软件工程效率和质量的关键因素。

"构建软件仍然需要纪律，但纪律更多地体现在支撑结构上，而不是代码上。保持代码库一致性的工具、抽象和反馈回路变得越来越重要。 我们当前最棘手的挑战集中在设计环境、反馈回路和控制系统方面，帮助智能体实现我们的目标：大规模构建和维护复杂、可靠的软件。"
— OpenAI 团队

未来的软件工程，人类将更多地扮演"骑手"的角色，通过设计优秀的 Harness 来引导 AI 这匹"骏马"奔向正确的方向，而不是亲自下场奔跑。
