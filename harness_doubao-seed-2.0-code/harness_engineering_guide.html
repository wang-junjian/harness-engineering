什么是 Harness Engineering？

🐴 马匹隐喻

  • 马 AI 模型 —— 强大、快速，但不知道该往哪里去
  • 缰绳 基础设施 —— 约束、护栏、反馈循环，引导模型的力量
  • 骑手 人类工程师 —— 提供方向，而不是亲自奔跑

📋 正式定义

Harness Engineering 是设计和实现以下系统的学科：

1
约束 - 定义 AI 智能体可以做什么（架构边界、依赖规则）
2
告知 - 让智能体知道应该做什么（上下文工程、文档）
3
验证 - 确认智能体正确完成了工作（测试、检查、CI 验证）
4
纠正 - 当智能体出错时进行修正（反馈循环、自修复机制）

🎯 模型是商品，Harness 才是护城河

LangChain 证明了这一点：他们的编码智能体在 Terminal Bench 2.0 上从 52.8% 提升到 66.5%， 从 Top 30 跃升至 Top 5 —— 没有改变模型，只改变了 Harness。

三大支柱

上下文工程

确保智能体在正确的时间拥有正确的信息。

静态上下文
  • • 仓库本地文档（架构规范、API 契约、风格指南）
  • • AGENTS.md 或 CLAUDE.md
  • • 经过检查器验证的交叉链接设计文档
动态上下文
  • • 智能体可访问的可观测性数据（日志、指标、追踪）
  • • 智能体启动时的目录结构映射
  • • CI/CD 流水线状态和测试结果

关键规则：从智能体的角度来看，任何它无法在上下文中访问的东西都不存在。Google Docs、Slack 线程或人们头脑中的知识对系统来说是不可见的。

架构约束

不是告诉智能体"写好代码"，而是机械地执行什么是好代码。

Types → Config → Repo → Service → Runtime → UI

每层只能向其左侧的层导入。这不是建议 —— 这是通过结构测试和 CI 验证强制执行的。

约束执行工具
  • • 确定性检查器 — 自动标记违规的自定义规则
  • • 基于 LLM 的审计器 — 审查其他智能体的代码以确保架构合规
  • • 结构测试 — 类似 ArchUnit，但用于 AI 生成的代码
  • • 预提交钩子 — 在提交任何代码前的自动化检查

悖论：约束解空间反而使智能体更高效。当智能体可以生成任何东西时，它会浪费 token 探索死胡同。当 Harness 定义了清晰的边界时，智能体会更快地收敛到正确的解决方案。

熵管理（垃圾回收）

随着时间推移，AI 生成的代码库会积累熵 —— 文档偏离现实、命名约定发散、死代码堆积。

定期清理智能体
  • • 文档一致性智能体 — 验证文档与当前代码匹配
  • • 约束违规扫描器 — 查找通过早期检查的代码
  • • 模式执行智能体 — 识别并修复与既定模式的偏差
  • • 依赖审计器 — 跟踪并解决循环或不必要的依赖

这些智能体按计划运行 —— 每日、每周或由特定事件触发 —— 保持代码库对人类审阅者和未来 AI 智能体都健康可用。

前馈（Feedforward）

预测智能体的行为并在行动前进行引导。增加智能体在第一次尝试中产生好结果的概率。

反馈（Feedback）

在智能体行动后观察并帮助其自我修正。当产生为 LLM 消费优化的信号时特别强大。

计算型 vs 推理型控制

⚡ 计算型

确定性且快速，由 CPU 运行。

  • • 测试
  • • 检查器
  • • 类型检查器
  • • 结构分析

毫秒到秒级运行；结果可靠

🧠 推理型

语义分析、AI 代码审查、"LLM 作为法官"。

  • • 智能体代码审查
  • • 架构评审
  • • 语义重复检测
  • • 用户体验评估

通常由 GPU/NPU 运行。更慢更昂贵；结果更具不确定性

约束规则：

  • • 在每个业务领域内，代码只能"向前"依赖固定的层序列
  • • 横切关注点通过单一显式接口进入：Providers
  • • 通过自定义检查器和结构测试机械地执行这些规则
  • • 检查器错误消息在智能体上下文中注入修复指令

核心理念：不手动编写代码

工程师的工作重点转向了系统、架构和杠杆作用。不是"再努力一点"，而是问"究竟还需要什么样的能力，我们又该如何让这个能力对智能体来说既清晰可读又可强制执行？"

端到端自主能力

给定一个提示，智能体可以：验证状态 → 重现漏洞 → 录制演示视频 → 实施修复 → 验证修复 → 录制第二个视频 → 打开 PR → 回应反馈 → 检测并修复构建故障 → 合并（仅在需要判断时交由人工）

熵管理：定期垃圾回收

每周五 20% 的时间用于清理"AI 残渣" → 后来将"黄金原则"编码到系统中，建立循环清理流程。定期运行后台 Codex 任务扫描偏差、更新质量等级、发起有针对性的重构 PR。

Planner

将 1-4 句话的简单提示扩展为完整的产品规范。在范围上雄心勃勃，专注于产品上下文和高级技术设计。

Generator

一次一个功能地工作，每个冲刺结束时自我评估。协商冲刺合同：在编写任何代码前就"完成"的定义达成一致。

Evaluator

使用 Playwright 像用户一样点击测试，测试 UI 功能、API 端点和数据库状态。每个标准都有硬阈值。

设计原则：构建"可剥离"的 Harness

Harness 中的每个组件都编码了一个关于模型不能做什么的假设。当模型改进时，这些假设值得进行压力测试。随着模型变得更好，找到最简单的可能解决方案，只在需要时增加复杂性。

M

Mitchell Hashimoto 的 AI 采用之旅

从怀疑者到 Harness 工程师的六个步骤

1
放弃聊天机器人

立即停止尝试通过聊天界面执行有意义的工作。你必须使用一个智能体—— 至少能够读取文件、执行程序和发出 HTTP 请求。

2
重现你自己的工作

强迫自己用智能体提交重现所有手动提交。你会发现：将会话分解为清晰的任务、分离规划与执行、给智能体验证方法。

3
日终智能体

每天最后 30 分钟启动一个或多个智能体。深度研究、并行尝试不同想法、问题和 PR 分类/审查。

4
外包简单任务

让智能体做所有那些你非常有信心它们会得到基本正确解决方案的工作，同时你做其他工作。关闭智能体桌面通知。

5
工程化 Harness

每当你发现智能体犯错误时，花时间工程化一个解决方案，使智能体永远不会再犯那个错误。更好的隐式提示（AGENTS.md）+ 实际编程工具。

6
始终有一个智能体在运行

如果智能体没有在运行，问自己"现在有什么是智能体可以为我做的吗？"与更慢、更深思熟虑的模型结合使用效果特别好。

常见错误

❌ 过度工程化控制流

"如果你过度工程化控制流，下一个模型更新会破坏你的系统。" 构建你的 Harness 使其可剥离 —— 当模型变得足够智能不再需要时，你应该能够移除"智能"逻辑。

❌ 将 Harness 视为静态的

Harness 需要与模型一起演进。当新模型版本改进推理时，你的推理优化中间件可能会适得其反。每次重大模型更新时审查和更新 Harness 组件。

❌ 忽视文档层

最有影响力的 Harness 改进通常是最简单的：更好的文档。如果你的 AGENTS.md 模糊，你的智能体输出也会模糊。投资于精确的、机器可读的文档作为智能体的地面真理。

❌ 没有反馈循环

没有反馈的 Harness 是一个笼子，而不是指南。智能体需要知道它何时成功何时失败。内置：任务完成前的自验证步骤、作为智能体工作流一部分的测试执行、按任务类型的智能体成功率指标。
