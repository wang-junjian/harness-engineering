什么是 Harness Engineering?

Understanding the Concept

Harness 一词已成为 AI 智能体中除模型本身之外的一切 的简称。根据 Martin Fowler 的定义：

Agent = Model + Harness

在编码智能体的边界上下文中，Harness 包括：

  • 系统提示词 - 定义智能体的角色和行为准则
  • 工具集 - 智能体可以调用的能力集合（文件操作、代码执行、API 调用等）
  • 编排系统 - 控制智能体执行流程的机制
  • 上下文管理 - 相关信息检索和注入策略
  • 反馈机制 - 自我纠正和改进的循环

核心目标： 增加智能体第一次就做对的概率，并提供反馈循环以自我纠正尽可能多的问题，甚至在问题到达人类视线之前。

Core Principles

Feedforward 与 Feedback 控制循环

Feedforward (前馈控制)

Guides - 预期智能体行为，在其行动之前进行引导

  • 增加首次生成高质量结果的概率
  • 系统提示词、技能定义、架构文档
  • 编码规范、最佳实践指南

Feedback (反馈控制)

Sensors - 观察智能体行动后，帮助其自我纠正

  • 为 LLM 消费优化的信号（如包含修复指令的 linter 消息）
  • 代码审查智能体、静态分析、日志分析
  • 测试结果、覆盖率报告

Computational 与 Inferential 执行类型

Computational (计算性)

●

确定性强，速度快，由 CPU 运行

●

测试、Linter、类型检查器、结构分析

●

毫秒到秒级运行；结果可靠

优势：足够便宜和快速，可以在每次更改时与智能体一起运行

Inferential (推理性)

●

语义分析、AI 代码审查、"LLM 作为裁判"

●

通常由 GPU 或 NPU 运行

●

较慢且昂贵；结果更非确定性

优势：允许提供丰富的指导，并添加额外的语义判断。在使用强模型或适合任务的模型时特别增加信任

  • • 创建功能列表

  • • 按规格实现功能
  • • Sprint 迭代开发

上下文管理架构

基于 OpenAI 的实践经验，有效的上下文管理是智能体在大型复杂任务中成功的关键：

❌ 反模式：单一大型 AGENTS.md

  • ✗ 上下文是稀缺资源，大文件挤掉任务和代码
  • ✗ 过多指导变得无效，智能体本地模式匹配而非导航
  • ✗ 立即腐化，变成过时规则的坟场
  • ✗ 难以机械检查，漂移不可避免

✅ 最佳实践：结构化知识库

  • ✓ AGENTS.md 作为目录地图（约 100 行）
  • ✓ 深度信息存储在结构化 docs/ 目录
  • ✓ 渐进式披露：从稳定切入点开始
  • ✓ 通过 linter 和 CI 验证知识库完整性

最佳实践

Best Practices

ar
1

为智能体进行上下文工程

上下文组装对智能体仍然困难，尤其是在未见过的环境中。通过为智能体提供目录结构、可用工具、编码最佳实践和问题解决策略，减少搜索错误和规划中可避免的错误。

关键点：为智能体入职，就像为新团队成员提供引导一样。将产品原则、工程规范和团队文化信息提供给智能体，带来更一致的输出。

2

帮助智能体自我验证工作

模型倾向于其第一个合理解决方案。激进地提示它们通过运行测试和完善解决方案来验证工作。这在没有人类在循环中的自主编码系统中特别重要。

自验证循环：规划与发现 → 构建（包含测试）→ 验证（运行测试）→ 修复

3

将追踪作为反馈信号

追踪使智能体能够自我评估和调试自己。重要的是同时调试工具和推理（例如，模型走错路径是因为缺乏工具或不知道如何做某事）。

应用：使用 LangSmith 等工具存储智能体操作，包括延迟、Token 计数和成本指标。创建 Trace Analyzer Skill 来分析跨运行错误。

4

检测并修复短期内的坏模式

今天的模型并不完美。Harness 设计师的工作是设计解决当前缺陷的方案，同时为未来更智能的模型规划。盲目重试和不验证工作是常见问题。

示例：LoopDetectionMiddleware 跟踪每次文件编辑计数，在 N 次编辑后添加上下文如"...考虑重新考虑您的方法"

5

构建分层领域架构

智能体在具有严格边界和可预测结构的环境中最高效。围绕严格的架构模型构建应用，每个业务域划分为一组固定层，依赖方向严格验证。 

Types → Config → Repo → Service → Runtime → UI

    Providers (单一显式接口)
6

建立垃圾回收机制

技术债务就像高息贷款，不断小额偿还比积累然后痛苦解决更好。将"黄金原则"编码到代码库中，建立循环清理流程。

实施：定期运行后台智能体任务，扫描偏差、更新质量等级、发起有针对性的重构 PR。大多数可以在一分钟内审查并自动合并。

关键洞察总结

构建软件仍然需要纪律，但纪律更多地体现在支撑结构上，而不是代码上

保持代码库一致性的工具、抽象和反馈回路变得越发重要

人类工程师的目标是让智能体能够直接从代码库推理出完整的业务领域

优秀的 Harness 不一定旨在完全消除人类输入，而是将人类输入引导到最重要的地方

随着模型改进，Harness 空间不会缩小，而是移动，有趣的工程工作在于继续寻找下一个新颖的组合

当前最棘手的挑战：设计环境、反馈循环和控制系统
